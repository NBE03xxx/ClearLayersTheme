# Byte などの Canvas 対応テーマから Clear Layers への移行

Byte や Mercury など、Canvas のコンポーネント・テンプレートでサイトを構成しているテーマから、独立テーマ `clear_layers` へ移行するためのガイドです。[Drupal CMS のテーマガイド](https://project.pages.drupalcode.org/drupal_cms/customize/theme/)でも、Byte と Mercury は SDC を通じて Canvas と連携するテーマとして説明されています。

このプロジェクトでは、生成AIへのプロンプトで移行を指示し、Byte から新テーマへの移行と Byte 関連ファイルの削除を進めた経験があります。その経験を踏まえ、まず **生成AIに実際のプロジェクトを調査させ、移行処理の作成・検証・不要ファイルの整理まで依頼する方法**を紹介します。後半には、手動で進める場合や、AIが提示した計画を確認する場合の参考手順を残しています。

以下は、Linux サーバーに SSH で接続し、Codex CLI を使う一例です。当時の操作履歴やプロンプトの再現ではありません。OS、権限、公開ディレクトリ、Drupal・Canvas のバージョン、インストール方法によって内容を調整してください。他の生成AIツールを使う場合も、プロジェクトのファイルを参照・編集し、必要なコマンドを実行できる環境を用意するという考え方は共通です。

**既定テーマの切り替えだけでは、保存済みの Canvas 構成を Clear Layers の部品へ移せません。** このテーマには Byte・Mercury 用の汎用的な自動移行ツールや互換性を保証する対応表はありません。AIには移行元の構成と保存済みデータを調べさせ、そのサイトに合う方法を組み立ててもらいます。

## 生成AIを活用する移行例：SSH と Codex CLI

### 1. 作業先と復元できる状態を用意する

本番サイトを複製した検証環境を作業先とし、データベース・アップロードファイル・コード・設定のバックアップを用意します。Git の差分で確認できるのは管理対象のファイルです。Canvas の保存済みページやデータベースの変更は、別途バックアップと Drupal API による検証が必要です。

検証環境に、移行元テーマと Clear Layers の両方を配置します。Clear Layers の取得と依存モジュールの準備は [README のインストール手順](../README.md#インストール)を参照してください。この段階では、移行元テーマを削除したり、本番の既定テーマを変更したりしません。

次の例の `deploy@server.example` と `/var/www/example-site` は、それぞれ接続先と検証用 Drupal プロジェクト直下に置き換えます。プロジェクトには `composer.json`、`vendor/bin/drush`、公開ディレクトリなどがあり、Drush が検証用データベースを参照する状態にしてください。

手元の端末から接続します。

```sh
ssh deploy@server.example
```

以降のコマンドは SSH 接続先で実行します。

```sh
cd /var/www/example-site
pwd
vendor/bin/drush status
```

作業ユーザーには必要なファイルの編集と Drush の実行権限を用意します。複数サイトを管理する構成では、対象サイトの URI や Drush エイリアスも指定してください。ここでは、SSH 接続先で CLI を動かし、サーバー上のプロジェクトを作業対象にします。

### 2. Codex CLI を導入して認証する

[OpenAI の Codex CLI 公式ガイド](https://learn.chatgpt.com/docs/codex/cli)に従い、作業ユーザーでインストールします。Linux 向けの公式インストーラーを使う例です。導入済みならインストールは省略します。

```sh
curl -fsSL https://chatgpt.com/codex/install.sh | sh
codex --version
```

インストーラーが案内する PATH の設定が必要な場合は反映してください。サーバーの OS・CPU やソフトウェア導入方針に合わない場合は、公式ガイドの別の導入方法を使います。

ブラウザーを持たない SSH 接続先では、デバイスコードによる認証を使う例があります。

```sh
codex login --device-auth
```

表示された URL を手元のブラウザーで開き、コードを入力して認証します。アカウントやワークスペースでデバイスコード認証の有効化が必要な場合があります。利用できない場合の方法は [OpenAI の認証ガイド](https://learn.chatgpt.com/docs/auth)を参照してください。認証情報はプロジェクトのファイルやプロンプトに含めません。

### 3. AGENTS.md に作業方針を記述する

Drupal プロジェクト直下に `AGENTS.md` を用意します。既にある場合は、現在の指示を確認して移行作業の範囲を追記・調整してください。[Codex の AGENTS.md ガイド](https://learn.chatgpt.com/docs/agent-configuration/agents-md)で説明されているように、作業ディレクトリまでの指示が読み込まれます。テーマなどの別ディレクトリを扱う場合は、その配下の指示も確認するよう依頼します。

以下は、公開ディレクトリが `web` の場合の記述例です。パス・保持方針・変更範囲を実際の環境に合わせて調整して保存します。

```markdown
# Drupal テーマ移行の作業指示

- 回答・進捗・作業結果は日本語で記述する。
- 対象はこのプロジェクトの検証環境。移行元は Byte、移行先は Clear Layers。
- 開始時に Drupal・Canvas・テーマのバージョン、公開ディレクトリ、
  Drush の対象サイト、作業範囲にある AGENTS.md を確認する。
- 移行先テーマの機械名は clear_layers。独立テーマとして base theme: false を維持する。
- 通常のコード変更は web/themes/custom/clear_layers 配下に限定する。
  Core・contrib・vendor のソースを直接改変しない。
- composer.json・composer.lock・設定・テーマ外の変更が必要な場合は、
  理由、変更対象、実行コマンドと影響を提示し、承認された範囲で進める。
- SQL による直接変更は禁止。設定・コンテンツの移行には Drupal API を使う。
- 本文・メディア・メニュー・URL・公開状態・翻訳を保持する。
  下書き・自動保存・リビジョンの扱いは、調査結果と保持方針に基づいて決める。
- SDC の ID・バージョン・props・slots・フィールド参照を確認し、
  名前の一括置換だけで移行を済ませない。
- 移行元テーマと関連パッケージの削除は、移行・検証・依存監査の後に行う。
  共有する部品やパッケージ、履歴に必要なものを削除しない。
  Composer 管理のものは Composer で整理する。
- 実サイトの本文・書き出し・バックアップ・認証情報を公開リポジトリに含めない。
- 作業結果には変更ファイル、設定・データの変更、検証結果、未解決事項、
  削除したものと保持したもの、復元方法を記載する。
```

`AGENTS.md` は作業方針を伝える文書です。実際に使える権限は、作業ユーザーと Codex の権限設定でも確認します。

### 4. 調査と移行計画を依頼する

Drupal プロジェクト直下から起動します。

```sh
codex
```

最初は調査を依頼します。パスと対象は自分の環境に置き換えてください。

```text
この検証環境の Byte テーマから Clear Layers へ移行したいです。
最終的には、不要になった Byte 関連ファイル・設定・パッケージも整理してください。

まず AGENTS.md と変更対象ディレクトリの指示を読み、読み取り専用で調査してください。
まだ設定・コンテンツの保存、既定テーマの変更、アンインストールや削除はしないでください。

Clear Layers は web/themes/custom/clear_layers にあります。
Drupal・Canvas・テーマのバージョンと Drush の接続先を確認し、
以下を含む移行計画を提示してください。

- Byte の SDC を参照するページ、コンポーネントフィールド、パターン、
  コンテンツテンプレート、PageVariant、残存する PageRegion。
- 部品ごとの移行先候補と、props・slots・保存済みバージョン・フィールド参照の変換。
- 共通ヘッダー・フッター、ブロック配置、ロゴ、配色、画像・ライブラリの移行。
- 翻訳、下書き、自動保存、過去・未公開リビジョンに残る依存と、保持方法。
- バックアップと復元方法、必要な設定変更・コマンド、検証手順。
- Byte 関連の削除候補、その根拠、他の機能と共有するものや保持が必要なもの。

移行元の機械名やコンポーネント ID を推測せず、実際の定義とデータで確認してください。
足りない情報は質問し、調べられなかった範囲は明示してください。
```

### 5. 確認した計画の実装と検証を依頼する

計画を確認し、バックアップの保存先・下書きと履歴の保持方針・許可する変更範囲を具体的に伝えます。次の例の角括弧部分は実際の内容に置き換えます。

```text
提示した計画に沿って、この検証環境の移行を実装・実行してください。
バックアップは [保護された保存先] にあり、復元手順は [確認した方法] です。
下書き・自動保存・リビジョンは [合意した保持方針] に従って扱ってください。
承認するテーマ外の変更とコマンドは [確認済みの対象とコマンド] です。

必要なら Clear Layers 配下にサイト専用の移行処理を作成し、
読み取り専用の計画で対象と変換結果を確認してから Drupal API で適用してください。
既存データを保持し、失敗時に途中の変更をどう戻すかを明示してください。
サイト専用データを含むスクリプトや書き出しは公開リポジトリへ追加しないでください。

既定テーマ、Canvas の部品・レイアウト、通常のブロック配置、テーマ設定を移行し、
データ診断と表示・編集・プレビュー・公開を検証してください。
自動で確認できなかったブラウザー操作は、私が確認できる具体的な手順を示してください。
Byte のアンインストールとファイル削除は、次の依存監査後に行います。
```

AIが作成した変更は差分と実行結果で確認します。診断結果だけでなく、実際のページ表示と Canvas の操作も確認してください。AIにブラウザー操作環境がない場合は、その確認を利用者が補います。

### 6. Byte 関連の整理まで依頼する

検証が済んだら、不要になった関連ファイルまで調査・整理を依頼します。ファイル名に `byte` が含まれることだけを削除の根拠にはしません。

```text
移行後の表示と Canvas の操作を確認しました。
Byte を使わずに運用できる状態に仕上げてください。

まず、設定・コンテンツ・翻訳・下書き・全リビジョン・コード・パッケージからの
Byte への参照と依存を監査し、削除対象と実行コマンドを提示してください。
必要なものが残る場合は、保持方針を守って解消する方法を提示してください。
履歴やコンテンツの削除で依存を消すことはしないでください。

監査で不要と確認し、私が承認した対象について、テーマのアンインストール、
Composer パッケージの整理、不要ファイル・設定の削除まで実施してください。
他の機能で使う共有パッケージや部品は保持してください。
削除後にデータ診断と代表ページの検証を再実施し、
削除したもの、残したもの、その理由、未確認の範囲を報告してください。
```

このように、目的・保持条件・完了条件を伝え、AIが実サイトの構成に合わせて調査と実装を進める形にします。「関連ファイルをすべて削除できた」という結果は、そのサイトの依存を解消できた場合の結果です。必要な履歴や共有機能に依存が残るサイトでは、移行元の一部を保持するか、追加の移行処理を用意します。

検証環境で確認した変更と手順を本番へ反映する場合は、対象環境・最新バックアップ・反映方法を改めて指定します。本番への適用と復元で確認する内容は、後半の参考手順にも記載しています。

## 参考：手動による移行と確認事項

ここからは手動で移行する場合の手順です。生成AIに依頼する場合も、調査・計画・検証で扱うべき内容を確認する資料として使えます。記事・メディア・メニュー・Views などの既存データを生かしながら、表示と Canvas の構成を移します。テーマのインストールだけでは、これらのデータや Clear Layers 用のページ・テンプレートは作成されません。

### 1. テーマに依存する箇所を把握する

Canvas はページにコンポーネントの ID・バージョン・入力値・親子関係を保存します。テーマが提供する SDC は提供元テーマへの依存を持ち、同じ「Hero」「カード」という名前でも別テーマの部品とは別物です。テーマを削除すると保存済みコンテンツに影響する問題は、[Canvas の課題 #3567586](https://git.drupalcode.org/project/canvas/-/work_items/3567586)でも扱われています。具体的な挙動は導入しているバージョンで確認してください。

移行対象を次の単位で記録します。

| 対象 | 確認する内容 |
| --- | --- |
| Canvas ページ・コンポーネントフィールドを持つコンテンツ | 移行元 SDC の ID・保存済みバージョン、props、slots、フィールドやメディアへの参照 |
| コンテンツテンプレート | コンテンツタイプ・表示モードごとの適用先、動的なフィールドとの対応 |
| パターン | 共通ヘッダー・フッターなどの中にある SDC と、そのパターンの利用先 |
| ページ全体のレイアウト | PageVariant のコンポーネントと割り当て、既定の PageVariant。旧構成ではテーマ別 PageRegion も確認 |
| 通常の Drupal ブロック | 配置先テーマ・リージョン、表示条件、メニューや Views の設定 |
| テーマ固有の設定・アセット | ロゴ、配色、画像パス、Twig の部品参照、CSS クラス、ライブラリへの依存 |
| 公開状態以外のデータ | 翻訳、過去のリビジョン、未公開リビジョン、Canvas の自動保存に残る移行元参照 |

Clear Layers の検証基準は Drupal 11.4.9／Canvas 1.12.0 です。この構成の Canvas は、ページ全体を PageVariant で管理します。PageVariant 自体はテーマから独立していますが、その中の SDC や、移行元テーマのページテンプレートを表示するコンポーネントはテーマに依存します。PageVariant が残っているだけでは、移行元テーマを外せるとは限りません。

旧バージョンのテーマ別 PageRegion を使うサイトは、Canvas の更新手順とテーマ移行を分けて検証してください。更新で PageVariant に変換された場合も、移行元テーマへの依存が残っていないか調べます。リージョン名の変更や PageRegion のコピーだけを、すべてのサイトに共通する移行手順にはしません。

### 2. バックアップと検証環境を用意する

1. データベース、アップロードファイル、テーマ・モジュールのコード、依存パッケージのバージョン、設定を復元できる状態で保存します。バックアップは公開ディレクトリ外の保護された場所へ置きます。
2. 本番サイトの複製を検証環境に用意し、移行元テーマでの表示と Canvas の編集を確認します。
3. Canvas の未公開の自動保存を確認します。公開・破棄・別途保全の方針を決め、必要な下書きを失わないようにします。本番への適用中は編集と設定変更を止めます。
4. [README のインストール手順](../README.md#インストール)に従い、Clear Layers のファイルと必要な Twig Field Value・Twig Tweak を用意します。移行元テーマと、その部品が必要とする依存は残します。

以下のコマンド例は Drupal プロジェクト直下で実行します。公開ディレクトリが `web` 以外の場合はパスを読み替えてください。

検証環境で Clear Layers をインストールします。この時点では既定テーマを変更しません。

```sh
vendor/bin/drush theme:install clear_layers -y
```

Canvas の部品ライブラリは既定テーマによって表示対象が変わるため、インストールしただけでは Clear Layers の部品が選べない場合があります。次の切り替えは**検証環境で**行い、必要な SDC を Canvas のライブラリで有効にして、再構成と動作確認を進めます。

```sh
vendor/bin/drush config:set system.theme default clear_layers -y
vendor/bin/drush cr
```

この切り替えは、既存コンポーネントの置換、ブロック配置の移動、テーマ設定の変換を行いません。移行元テーマを残したままでも、既存部品の表示・編集に制約が出る可能性があるため、検証環境で確かめます。

### 3. コンポーネントとレイアウトを移す

#### 部品ごとの対応を決める

移行元の `.component.yml` と保存済み入力を、移行先の schema と比較します。SDC の提供元名や Canvas の `component_id` を一括置換する方法では、props の型・必須項目・enum、slots、保存済みバージョンの違いを解決できません。

次の Clear Layers 部品は用途から見た候補です。Byte の部品との互換性や一対一の対応を示すものではありません。

| 用途 | Clear Layers の候補 | 対応時に確認する例 |
| --- | --- | --- |
| Hero | `clear_layers:content-hero` | 見出し・本文・画像の入力、配置や高さの選択肢、追加コンテンツの slot |
| 記事カード | `clear_layers:article-card` | `heading_text`、リンク、画像、必須の `orientation`・`style`、任意の `date` |
| 記事ヘッダー・本文 | `clear_layers:article-header`、`clear_layers:content-text` | タイトル・日時・本文のフィールド参照、HTML の扱い |
| 共通ヘッダー・フッター | `clear_layers:shared-site-section` | `site_header`・`site_footer` パターンの準備と、その内部の部品 |

少数のページであれば Canvas の編集画面で部品を配置し直し、本文・画像・リンク・フィールド参照を対応させます。大量のページや履歴まで変換する場合は、Drupal API を使う個別の移行処理が必要です。SQL での直接変更は行いません。

個別処理では、変更対象を示す読み取り専用の計画、移行先 schema に合わせた入力変換、slots と親子関係の維持、移行先の有効なバージョンとの対応、保存前の検証、失敗時の復元方法を用意します。公開状態・翻訳・更新日時・リビジョンをどう扱うかも事前に決めてください。

#### ページ全体と共通部品を再構成する

1. 移行先の部品で PageVariant を作成または編集します。本文が入る「Page content」マーカーを保持し、ページとコンテンツテンプレートの割り当て、サイトの既定値を確認します。移行元テーマのページテンプレートを表示する部品がある場合は、その依存も解消します。
2. 共通ヘッダー・フッターをパターンで管理する場合は、`site_header`・`site_footer` を用意し、内部を Clear Layers の部品で構成します。同じ ID の既存パターンがある場合は、利用先を調べてから編集します。`shared-site-section` を置くだけではパターンは作成されません。
3. コンテンツテンプレートと各ページ内のパターン・部品を移し、タイトル・本文・日時・画像などの動的な参照を再設定します。
4. Canvas がページ全体を描画するルートでは、通常のテーマの `page.html.twig` やブロック配置だけを編集しても、期待したヘッダー・フッターにならない場合があります。Canvas のレイアウトと通常の Drupal ブロック配置をそれぞれ確認します。
5. ロゴ・配色・背景・余白は Clear Layers のテーマ設定で調整します。移行元テーマの設定をそのままコピーせず、画像パスやカスタム CSS・ライブラリも見直します。

公開リポジトリの starter-kit 適用ツールは、確認済みの書き出しを空のサイトへ導入するためのものです。既存の Byte サイトへ上書きして移行する用途には使いません。詳しくは [starter-kit の説明](../starter-kit/README.md)を参照してください。

### 4. 検証してから本番へ適用する

検証環境で、テーマの部品と Twig の読み込み、および Canvas のデータを診断します。

```sh
vendor/bin/drush php:script web/themes/custom/clear_layers/tests/theme-integrity.php
vendor/bin/drush php:script web/themes/custom/clear_layers/tests/canvas-health.php
```

これらはテーマ設定・コンテンツを変更しない診断です。Canvas の診断は導入バージョンの API に依存します。**診断に通ることと、移行元テーマへの参照がなくなることは別です。** 保存済みの部品が有効でも、移行元テーマを必要としている場合があります。依存監査は別途行ってください。

次を実際の表示と操作で確認します。

- トップページ、記事、一覧、検索、404、ログインと、Canvas を使わないページ。
- Canvas の編集・プレビュー・保存・公開、PageVariant とコンテンツテンプレートの適用。
- ヘッダー・フッター、メニュー、ロゴ、フィールド参照、画像、本文、リンク。
- スマホの表示、キーボード操作、明暗モード。
- 翻訳、下書き、自動保存、過去・未公開リビジョンを表示または復元したときの部品参照。

確認した変更対象・実行手順・復元手順をまとめ、本番への適用前に提示します。検証用データベースの丸ごと上書きは、本番で追加された記事やメディアを失うおそれがあるため、反映方法を事前に決めます。設定だけの反映では、Canvas ページなどのコンテンツエンティティは移行できません。

本番では編集を止めて最新のバックアップを取得し、検証済みの手順で設定・コンテンツ・既定テーマを反映してキャッシュを再構築します。その後、診断と代表ページの操作確認を行います。

#### Gin のメディアプレビューが縦長になる場合

通常の記事編集画面の Featured image、メディアグリッド、メディア選択ダイアログも確認します。Drupal 11.4.9／Gin 5.0.15 では、Claro の最小高さと Gin の幅に応じた余白が加算され、正方形のサムネイルでも表示枠が縦長になることがあります。画像スタイルの寸法変更では解消しません。

この場合は [Gin 用の補正 CSS](../css/gin-media-library.css)を、Gin が読み込む `public://gin-custom.css` に追加します。補正はメディアのグリッド表示枠を `aspect-ratio: 1` にし、加算される最小高さと余白を解除します。Clear Layers のフロント用 CSS には含めていません。

標準の公開ファイル配置で `gin-custom.css` が**存在しない場合**の例です。これはテーマ外のファイル配置を変更するため、プロジェクトの変更範囲・権限を確認してから実行してください。

```sh
cp --no-clobber web/themes/custom/clear_layers/css/gin-media-library.css web/sites/default/files/gin-custom.css
vendor/bin/drush cr
```

公開ファイルの配置先が異なる場合は `public://` の実際のパスに読み替えます。既存の `gin-custom.css` がある場合は、バックアップを取得してから補正ルールを追記し、既存のカスタマイズを保持します。Core・Gin の配布ファイルは変更しません。適用後は上記の各画面を再読み込みし、狭い画面でもプレビューが正方形になることを確認します。

Core・Gin の更新後も、補正なしで正方形になることを検証できるまでは補正を維持します。補正の削除条件と更新時の確認方法は [README の運用方針](../README.md#gin-のメディアプレビュー補正と更新時の扱い)を参照してください。

### 5. 移行元テーマの整理と復元

移行元テーマは、公開中のページだけでなく、テンプレート・パターン・PageVariant・残存 PageRegion・翻訳・下書き・リビジョンからの参照と設定依存が解消したことを確認してから、アンインストールを検討します。過去の履歴をそのまま保持する方針で移行元 SDC が残る場合は、そのテーマも保持します。アンインストールで依存設定の削除が示された場合は、対象を確認し、必要な構成が失われる操作を進めないでください。

移行元が Composer 管理の場合は、アンインストールと検証が済んだ後に、他の依存も確認してパッケージの削除を検討します。先にテーマのファイルやパッケージを削除しないでください。

復元は、変更した設定・コンテンツと対応するコード・ファイルを、バックアップから整合する状態へ戻します。既定テーマを戻すだけでは、置換した Canvas 部品や編集したレイアウトは元に戻りません。
